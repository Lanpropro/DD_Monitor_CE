# 插件商店与本体更新

> 类型：参考 ｜ 状态：维护中 ｜ 适用版本：0.7.x ｜ 更新：2026-11-16 ｜ 读者：贡献者、插件作者

## 更新下载进度

软件和插件更新通知在主窗口左上角提供直接下载入口，也可前往设置中的软件更新或插件页面操作。通知、软件更新页、商店卡片、已安装插件卡片及详情共用下载状态：点击下载后，原按钮的位置切换为细长进度条，旁边显示已下载／总大小与实际采样速度，不在下方新增进度行。校验期间继续显示进度；完成或失败后恢复原位操作按钮，分别提供重启或重试。

插件卡片按文本与固定操作区计算最小高度，进度文本保持单行，完整内容也可悬停查看。窄窗口或大字号下自动改用单列，避免信息和操作区相互挤压；下载前后保留同一操作位置。

本体和插件下载由主窗口持有；关闭通知或设置窗口不会重复下载或中断已有任务，重开页面恢复进度。插件分别显示各自进度及错误，失败可以重试；网络连接故障沿用最多三次尝试，重新开始时归零字节和速度。退出软件仍取消未完成任务并清理半成品。源码版不提供本体自动替换，插件仍可独立下载。

下载器日志记录每次连接耗时、接收字节、总耗时、尝试次数和连接错误类型，不记录签名下载地址或账号。用于真实网络慢速问题的后续采集；本次未增加第三方下载源或分段并发，不宣称网络速度改善。

人工从根 `run.cmd` 检查：在通知内下载一个更新，确认原通知出现进度条、大小和速度；前往对应设置页应显示同一进度，关闭重开设置不会重新下载。插件并发更新各自显示进度；断网失败有原因和重试入口，重试后进度重新开始。准备完成后提示重启但不自动退出，点击重启才保存并应用。真实冻结本体的升级、系统缩放与实际下载速度仍需分别验收。

离线功能回归：`run.cmd --check-update-progress`。使用临时插件目录、下载替身及测试数据，不访问真实账号或公网，不作为网络提速证据。

### 本地交互验收

从根目录运行 `run.cmd --preview-updates`，打开独立的「更新样式验收」窗口。无需创建 GitHub Release 或修改正式版本号。工具启动仅绑定 `127.0.0.1` 的临时 HTTP 服务，使用正式下载器与通知／设置控件，所有测试包、插件和计划放在系统临时目录；不读取真实账号、不更换程序、不装载测试插件。关闭窗口后停止下载、服务并清理临时目录。

通知中可分别点击软件或插件的「下载更新」，也可点「全部下载」；「前往设置」和右侧页面按钮可核对同一进度。关闭设置后继续，重新打开应保持进度。右侧可切换深浅色。

选好场景后点「重新开始」：正常下载约20秒，慢速约一分钟；断流场景先连续失败三次，再点击通知或设置中的重试入口即可恢复；校验失败场景首次摘要错误，重试恢复。下载完成后的「重启以应用」只显示已收到确认，不关闭真实客户端或安装本体。已开始下载时先等待完成，或关闭窗口重开后选择场景。

`run.cmd --preview-updates --smoke` 执行自动回归，使用更小的本机测试包检查实际传输、错误／重试及通知到设置的接线。受控本机传输只用于样式和交互验收，不代表真实 GitHub 网络速度或冻结 EXE 安装已通过。

设置 → 插件提供「已安装」「插件商店」两个页签。首次打开商店时读取官方仓库目录；选择安装或更新后后台下载并校验 SHA-256，保存并重启后生效。本体更新位于设置 → 软件更新，与插件版本独立。

本地待发布调整：软件更新按钮区分“请先检查更新”“检查中…”“已是最新版本”“下载更新”和“重启并更新”。不可下载时使用灰色外观及原因提示；发现新版才允许下载，失败后可重新检查或重试下载。“软件更新完成”是上次安装结果，不表示还有新版可下载。

插件商店目录保存在 `cache/plugin-catalog.json`，重新打开设置时立即使用缓存；每个设置窗口首次进入商店时后台重新核对在线目录和正式 Release，避免新发布的独立插件被旧缓存遮住。之后十五分钟内切换页签不重复查询，停留在商店时每十五分钟检测一次；有 ETag 时使用条件请求，内容未变化时保留原列表，有变化才自动更新。网络失败时保留已有目录。手动刷新按钮位于商店搜索栏右侧，与搜索框共用独立工具栏，避开页签和列表，可立即检查。

「已安装」与商店使用固定搜索栏、状态筛选、排序和结果数量。已安装列表支持按启用／禁用／可更新筛选，搜索名称、ID、说明与作者；筛选和排序保留未保存的启用选择。列表仅显示简短说明和状态，完整说明、加载失败原因及更新记录在「详情」中查看；详情更新与列表更新复用同一任务及待重启状态。列表独立滚动，末尾留白，与底部保存区分隔。

## 发布插件

下载来源固定为 `Lanpropro/DD_Monitor_Plugins` 的 Release。插件商店合并最新正式 Release 的 `plugin-catalog.json` 与近期正式 Release 安装包列表，按每个插件的最高版本选择，避免完整清单落后于独立插件的发布。草稿和预发布不进入商店；ZIP 的官方地址、大小、SHA-256和最低本体版本仍按原规则校验。公开 API 限流或离线时使用已获得的正式清单或本地缓存，无缓存则显示内置目录。

每个插件 `plugin.json` 建议声明 `min_app_version`，例如 `"0.3"`。生成目录时提供本次仍受支持的所有插件安装包，目录是完整列表，不仅包含本次改动的插件。

```powershell
python dev/tools/build_plugin_catalog.py --tag v1.1 --output plugin-catalog.json domestic_live-1.1.zip global_live-1.1.zip
```

将生成的目录和对应 ZIP 一起上传到同一正式 Release。工具只读取已有 ZIP，不执行插件代码或生成新 ZIP。每次升级使用新版本和新的附件 URL，不覆盖旧版本附件。

安装在下载后验证包 ID、版本及最低本体版本。新插件按现有安装器装载，不执行代码；已有插件暂存到 `plugins_user/.updates/<id>`，重启时在插件加载之前合并新文件并替换目录。保留原设置及包中未覆盖的数据文件，升级前在 `.updates/<id>.backup` 保留上一版本目录，替换失败恢复原目录。运行期间新增的数据在下一次启动时复制，避免下载后退出前的写入丢失。插件开发者应将运行数据与包内代码/资源分开，不在升级包中放入个人配置。

## 同步发布后修改的说明

维护者在 GitHub Release 页面修改 Markdown 后，可运行 `python dev/tools/sync_release_notes.py --version 0.5.1`，将该正式版本最新正文同步到本地 `docs/releases/RELEASE-v0.5.1.md`。线上正文为该文件的来源；内容相同不重复改写，查询失败或版本不符时保留本地文件。此操作不重新发布或修改已上传的 EXE ZIP，也不改软件版本号。技术清理与运行说明保留在本开发文档中，不要求维护者的 Release 文案重复全部技术细节。

EXE 默认启用独立设置进程，`DDM_SETTINGS_PROCESS=0` 可使用原设置窗口；打开设置不会改变播放或软件的版本号。

## 发布本体

0.3 开始包含更新助手。EXE 构建中生成 `ddm-build.json`，记录版本、Windows x64 平台和更新协议；生成 ZIP 时另在输出目录生成 `app-update.json`，包含版本、下载地址、大小、SHA-256 及更新说明。它们由正常发布脚本生成，不需要用户配置 GitHub Token。

正式发布时上传 **EXE ZIP 和 app-update.json**，并使用与本体版本一致的新 tag，例如 `v0.3`、`v0.3.1`。将该 Release 标记为最新正式版本。程序优先从最新 Release 的固定附件 URL 获取更新清单，兼容 GitHub Release API；草稿和预发布版本不会通过 API 推送。

### 同版本 Hotfix

本体按“版本号、内部修订号”依次比较。`ddm-build.json` 和 `app-update.json` 使用相同的非负整数 `revision`；缺少该字段的旧包按 0 处理。同一版本的修复包依次使用 1、2、3，升级到下一正式版本时可从 0 开始。修改发布说明或重新上传附件本身不算新修订；维护者必须递增修订号。

覆盖现有正式 Release 时，例如本体仍为 0.7.1：

```powershell
powershell -File dev/build_release.ps1 -UpdateRevision 1
```

将生成的 EXE ZIP 和 `app-update.json` 一起替换到原 Release。也可使用独立正式标签：

```powershell
powershell -File dev/build_release.ps1 -ReleaseTag v0.7.1-hotfix.1
```

`-hotfix` 等同于修订 1，`-hotfix.N` 使用修订 N；显式传入的 `-UpdateRevision` 必须与标签一致。生成清单中的 `release_tag` 决定下载地址及更新说明来源，打包程序名、窗口版本及 `version` 字段仍保持 0.7.1。界面标注“0.7.1 热修复”，不把内部修订号显示成 0.7.1.1。

手动检查和启动提醒都比较本地构建的修订号；已读提醒也区分每次修订。下载后额外核对包内修订号，安装成功后通过新构建记录停止重复提示；替换失败时随程序文件一起恢复旧记录。便携版和安装版均保留该记录。API 回退可读取同一 Release 的清单，也支持带 hotfix 后缀的正式标签。

此能力需要客户端先具备新的检查逻辑。既有旧版须先通过一次普通升级或手动覆盖获得该能力，不能只靠修改服务器清单让旧代码识别同版本修订。

软件更新先后台下载、验证版本及协议、检查路径和空间，再解压至系统临时目录。用户点击「重启并更新」才保存设置并正常收尾录制、播放器和插件。旧进程退出后，暂存的新程序以 `--apply-update` 启动助手，不初始化 Qt/libmpv，等待旧 PID 退出、备份并替换程序文件，然后启动新版。助手启动失败时保留原程序；替换失败时恢复已替换的文件，并在更新页显示结果。

「自动更新」是保存到设置的开关，默认关闭。开启后启动软件时在后台检查本体新版；有新版时显示左上角悬浮提示，不抢焦点、不使用模态弹窗。通知提供「下载更新」及「前往设置」；用户确认下载后，原通知显示进度并保持可见，下载完成后再由用户确认重启。

启动时也会检查已安装插件的可用新版，复用商店缓存和十五分钟检查间隔，不受本体自动更新开关影响。仅有插件更新时，提示按钮进入插件商店；本体和插件都有更新时合并提示，优先进入软件更新页。检测到更新后，主界面设置入口和设置中对应的导航右侧显示红点，插件商店页签及可更新插件按钮的右侧也显示红点。确认没有新版、删除对应插件或插件更新已下载等待重启后，清除对应标记。

点击设置入口后清除入口的红点，尚未查看的更新页仍保留标记。用户查看对应更新页面后，即使暂不安装，也会清除该版本的红点并保存已查看记录；同一版本不再重复提示，更高版本仍会重新提醒。关闭悬浮提示本身不算查看，更新按钮保持可用。提示栏使用软件主题的浮层背景色。

「更新说明」区域按 Markdown 展示对应版本的 GitHub Release 正文，发布后修改正文会在下次检查时重新读取；读取失败时使用更新清单中的 `notes`。没有新版时也会尝试读取当前版本的线上正文；未检查或网络失败时使用源码目录 `docs/releases/` 或 EXE 同级附带的当前版本 `RELEASE-v*.md`，缺少文件时提示前往发布页查看。发布脚本仍将 `docs/releases/RELEASE-v*.md` 写入清单，供离线或 API 限流时备用；更新包地址、大小和 SHA-256 不因正文更改而改变。

关闭设置窗口不会取消本体或插件更新下载；同一次软件运行中重新打开设置会恢复同一下载任务、进度和说明。后台完成后由用户点击重启并保存才应用。退出软件会停止未完成下载并清理未确认安装的本体暂存包；不跨软件退出保存下载断点。已暂存成功的插件仍按原流程在下一次启动时应用。

`utils`（含关注配置、账号凭据）、`cache`、`logs`、`plugins_user` 和录制目录不会被更新包覆盖。程序文件清单用于后续更新清理过期运行库，未记录的用户文件保留。临时程序和备份在更新完成后的正常启动中清理，文件仍占用时留待后续启动。

源码版可以检查新版和打开发布页，自动替换仅用于 EXE 版。旧 v0.2 EXE 没有更新入口，第一次需手动升级至包含该功能的版本；之后才能在线更新。

开发验证：`selfcheck_online.py`、`selfcheck_online_ui.py` 和 `selfcheck_update_install.py` 覆盖校验失败、取消、兼容性、插件暂存及回滚、用户数据保留、Windows 父进程等待和录制退出接入。正式发版还需用真实冻结 EXE 在隔离目录中完成一次跨版本升级验收。

0.3.1 作为固定程序名的过渡版本，额外提供 `DD监控室CE-v0.3.1.exe`，供旧 0.3 更新器识别；该入口启动后转交给 `DD监控室CE.exe`。之后的发布包只提供固定名称主程序，版本信息仍在更新清单和 Windows 文件属性中保留。

EXE 包内程序目录及日常启动文件固定为 `DD监控室CE/DD监控室CE.exe`，在线更新保留原安装目录，避免按路径设置的白名单因版本号变化而失效。手动更新请解压覆盖原目录。

新用户安装包为 `DDMonitorSetup.exe`，安装时建立初始程序文件清单。安装、卸载边界和验证见 [Windows 安装包](development/windows-installer.md)。卸载保留个人数据与未登记文件，不以递归删除清空安装目录。

## 无旧清单的历史版本清理

新版冻结 EXE 启动后，在后台核对历史发布包清单，补处理旧便携版或多次覆盖升级遗留的程序文件。源码运行和更新助手不会执行。构建脚本在最终便携目录生成 `ddm-program-inventory.json`，记录本版本实际程序路径；该文件随在线更新 ZIP 和 Setup 一起安装。版本不匹配或清单缺失时保留原文件。

历史目录为 `ddm/assets/update/legacy-program-files.json`，从本地 0.1、0.2、0.3、0.3.1、0.4、0.5 六份 EXE 发布 ZIP 生成，记录归档 SHA-256、程序文件路径、大小和各已知内容哈希。生成时排除用户数据目录，不将其配置内容读入清单。新版仍使用的路径始终保留；只有已知旧路径、大小及 SHA-256 全部匹配才会移出。用户改动过的旧文件、未知文件、账号、插件、录制、缓存和日志均不参与此兼容清理；目录链接和占用中的文件跳过，后续启动可重试。

旧文件移动到安装目录的 `work/legacy-program-backup-*/files/`，相对路径保持不变，旁边有 `cleanup-report.json`。不递归清空旧运行库目录，不自动删除恢复备份，因此本步骤清理运行目录，不直接释放备份占用的磁盘空间。需要恢复时，退出软件后按报告将 `files/` 内对应文件复制回原相对路径；确认新版本稳定后可自行删除该批备份。更新器继续保护整个 `work/`。

重新生成历史清单：

```powershell
python dev/build_program_inventory.py --archives <各版本EXE-ZIP路径> --output ddm/assets/update/legacy-program-files.json
```

正常发布构建自动生成当前清单；单独验证目录可用 `python dev/build_program_inventory.py --payload <干净的最终便携目录>`。`check_release_package.py` 会核对清单与最终 EXE ZIP 的文件集合一致。只有重新构建、安装包含本功能的新版本后才生效；不修改已发布的旧 EXE 或更新协议。
