# 开发文档规范

> 类型：规范 ｜ 状态：维护中 ｜ 适用版本：0.7.x ｜ 更新：2026-11-14 ｜ 读者：维护者、贡献者、插件作者、网站维护者

## 本页内容

全流程与文档动作、文档分层、类型与元信息、命名与路径、写作规则、版本与跨仓库约定、生命周期与归档、
索引与新增流程、自动化校验、模板、例外与迁移。第一次使用先读第 1 节和第 8 节，再按需要查第 3、5 节。

本规范约束 DD监控室CE 的全部开发文档，并作为软件本体、插件仓库、网站仓库的共享基线。
目标是让每个参与者在同一条流程里知道：现在该写哪份文档、写在哪里、写到什么程度算完成。

- 软件本体：[DD_Monitor_CE](https://github.com/Lanpropro/DD_Monitor_CE)（本仓库）
- 插件源码：[DD_Monitor_Plugins](https://github.com/Lanpropro/DD_Monitor_Plugins)
- 展示网站：[DD_Monitor_Website](https://github.com/Lanpropro/DD_Monitor_Website)

## 1. 全流程与文档动作

一项改动从提出到可回滚，按下面的顺序推进。每一步都有对应文档；没有产出的步骤要在 PR 或交接中说明原因，
不能默认为“已经做过”。

| 阶段 | 要回答的问题 | 文档产出 | 位置 |
| --- | --- | --- | --- |
| 需求与范围 | 改什么、不改什么、如何判定完成 | Issue 表单、验收条件；已复现故障进入案例库 | `.github/ISSUE_TEMPLATE/`、[Bug 案例库](../bug-cases.md) |
| 设计 | 状态归谁、边界在哪、失败如何收场 | 架构说明、设计说明；插件写 `DESIGN.md` | [架构总览](../architecture/overview.md)、`docs/`、插件目录 |
| 实现 | 代码放在哪个职责模块 | 模块文档字符串、`docs/development/` 中的职责说明 | `ddm/`、`plugins/<ID>/` |
| 验证 | 哪些检查通过、哪些仍需人工 | 验证命令与结果；专项索引；插件验收清单 | [验证指南](../development/testing.md)、`dev/checks/`、插件 `ACCEPTANCE.md` |
| 变更记录 | 这一版实际改了什么 | 未发布记录；插件增量记录 | [UNRELEASED](../releases/UNRELEASED.md)、插件 `docs/changes/` |
| 发布 | 版本、源码 SHA、产物、兼容范围 | 发布说明、标签、网站下载数据 | [发布记录](../releases/README.md)、插件 `docs/releases/`、网站 `docs/data/` |
| 网站同步 | 用户看到的信息是否与已发布产物一致 | 版本、下载地址、SHA-256、插件目录 | 网站仓库 `docs/data/*.json`，由同步工具生成 |
| 归档 | 历史是否可追溯 | 归档索引、冻结说明 | [历史记录](../archive/README.md)、插件 `docs/archive/` |

顺序原则：本体与插件各自独立版本；网站只同步**已经发布**的资产，不读取开发目录中的本地构建包。
跨仓库发布顺序通常是：本体发布 → 兼容插件发布 → 网站同步。插件先于本体发布时，必须在插件清单和说明中
写清最低本体版本，不能假设网站或用户会先看到新本体。

## 2. 文档分层

每个仓库都按同一套分层组织文档，文件名保持稳定，避免为了“整理”反复移动导致链接失效。

| 层 | 作用 | 本体 | 插件仓库 | 网站仓库 |
| --- | --- | --- | --- | --- |
| 入口 | 第一眼看到什么 | 根 `README.md`、`CONTRIBUTING.md`、`docs/README.md` | 根 `README.md`、`CONTRIBUTING.md`、`docs/README.md` | 根 `README.md`、`CONTRIBUTING.md`、`development/README.md` |
| 规范 | 共同遵守的规则 | `docs/standards/` | `docs/standards/` | `development/` |
| 架构 | 系统如何组成、边界在哪 | `docs/architecture/` | 插件目录说明与各插件 `DESIGN.md` | `WEBSITE.md`、`development/content-sync.md` |
| 开发指南 | 环境、测试、构建、排障 | `docs/development/` | `docs/development/` | `development/`、`WEBSITE.md` |
| 设计与参考 | 功能说明、接口、文件清单 | `docs/*.md`、`docs/repository-map.md` | 各插件 `README.md`、`FEATURES.md`、`PARITY.md` | 发布后的 `docs/` 页面（面向用户） |
| 记录 | 版本、变更、验收、故障 | `docs/releases/`、`docs/bug-cases.md` | `docs/changes/`、`docs/releases/` | `docs/data/` 与 PR 记录 |
| 归档 | 不再更新的历史 | `docs/archive/` | `docs/archive/` | `MIGRATION.md` 与 Git 历史 |

根目录只保留仓库入口文件（`README.md`、`CONTRIBUTING.md`、`AGENTS.md`、`LICENSE`、本机交接入口）。
新的专题文档进入对应子目录，不继续堆在根目录或 `docs/` 顶层。

## 3. 文档类型与元信息

长期维护的文档（`docs/**/*.md` 与各仓库根目录指南，发布说明和历史归档除外）在第一行标题下写一行元信息：

```markdown
> 类型：指南 ｜ 状态：维护中 ｜ 适用版本：0.7.x ｜ 更新：2026-11-14 ｜ 读者：贡献者
```

| 字段 | 允许值 | 说明 |
| --- | --- | --- |
| 类型 | `规范`、`架构`、`指南`、`参考`、`设计`、`记录`、`索引` | 决定该文档的写法与更新时机 |
| 状态 | `草案`、`维护中`、`稳定`、`冻结`、`历史` | `草案` 可变；`稳定` 改动需评审；`冻结` 只补勘误；`历史` 不再代表当前行为 |
| 适用版本 | `0.7.x`、`全部版本`、`不适用` | 写主体版本族；发布新小版本时统一复核 |
| 更新 | `YYYY-MM-DD` | 最近一次**内容**变更日期，不使用“今天”“最近” |
| 读者 | 角色列表，用顿号分隔 | 例：`维护者、贡献者`、`插件作者`、`用户` |

豁免：`README.md`、`CONTRIBUTING.md`、`LICENSE`、`NOTICE.md`、`docs/archive/` 下的历史记录、各仓库的发布说明与
经哈希固定的历史文件。插件仓库的 `docs/releases/` 受 `sources.json` 哈希约束，**不得为了排版改写**。

文档类型的基本要求：

- **规范**：写“必须/禁止/允许”，每条规则尽量可检查。
- **架构**：写职责、依赖方向、状态所有权和生命周期，不复制完整文件清单。
- **指南**：写可执行步骤与预期结果，命令从仓库根目录开始。
- **参考**：写接口、字段、文件归属和兼容范围；变化时同步调用方。
- **设计**：写范围、交互、边界和失败处理；实现完成后保留决策理由。
- **记录**：按时间追加，写清版本、提交、验证与结论；结论不确定就写不确定。
- **索引**：只做导航与状态说明，不复制正文。

## 4. 命名与路径

- 长期文档使用小写英文加连字符：`image-cache.md`、`windows-installer.md`。
- 文件名不使用空格、中文或下划线；已有历史文件保持原名，不为改名制造链接断点。
- 版本说明使用 `RELEASE-v<本体版本>.md`、`RELEASE-<插件ID>-v<插件版本>.md`；插件记录使用 `PLUGIN-<插件ID>-v<版本>.md`。
- 带日期的记录使用 `<主题>-<YYYYMMDD>.md`，日期是记录日期，不是计划日期。
- 图片与素材放在被引用文档附近的 `assets/` 或既有资源目录；正文使用相对路径，不嵌入本机绝对路径。
- 跨仓库引用使用完整 GitHub URL；不使用 `../DD_Monitor_Plugins/...` 这类只在本机成立的路径。

## 5. 写作规则

### 5.1 先结论，后证据

每节第一段写结论和当前状态，再写原因、命令和证据。长段落优先拆成表格或短列表；不要用时间顺序代替结构。

### 5.2 状态词统一

| 状态 | 含义 | 不能写成 |
| --- | --- | --- |
| 已实现 | 代码已在本分支 | 已修复、已解决 |
| 已验证（隔离） | 离屏/替身/合成数据检查通过 | 已验收 |
| 已人工验收 | 维护者按步骤在真实运行中确认 | 已全量验证 |
| 已发布 | 版本标签与公开产物对应 | 已合并、已推送 |
| 待验收 | 有实现和证据，缺用户或真实运行确认 | 已完成 |
| 待定位 / 待复现 / 暂缓 | 现象与证据保留，根因未确认 | 已知问题（含糊） |

禁止把“自动检查通过”直接写成“用户问题已解决”；禁止把“已合并”写成“已发布”；禁止用旧版本验收
代替当前版本的验收。

### 5.3 日期、版本与提交

写绝对日期、明确版本和可回溯的提交 SHA。示例：`2026-11-13 在 0.7.3 源码 + PySide6 6.11.2 下复测`。
引用提交时写短 SHA 全称（至少 8 位）并说明所在分支；不要只写“最新提交”。

### 5.4 证据分层

涉及性能、卡顿、播放和原生窗口时，必须区分以下证据，不得互相替代：

1. 静态检查与仓库规范（不运行程序）；
2. 离屏回归（合成数据、替身接口、临时配置）；
3. 原生回归（真实窗口、libmpv、FFmpeg，本机屏幕外）；
4. 真实运行（真实账号、真实直播、真实录制与人工观察）；
5. 用户验收（用户明确确认的版本和操作范围）。

文档写明执行到哪一层、哪些未执行。未执行的检查写“未执行”，不写“预计通过”。

### 5.5 命令、代码与链接

- 命令使用 `powershell` 代码块，默认从仓库根目录执行；换目录时写明。
- 不在文档中放真实 Cookie、令牌、账号、录制内容或含隐私的截图。
- 相对链接必须能在克隆后的仓库中解析；锚点指向真实标题。
- 引用外部资料时给出可访问链接，并注明访问日期或资料版本。

### 5.6 结构与长度

- 超过约 200 行的长期文档在标题后提供“导读”或“目录”，说明本页用途、推荐阅读顺序和关键小节。
- 追加型记录（未发布记录、验证日志）按时间或版本分段，最新在前或最新在后必须写清；顶部保留阅读方式。
- 表格用于矩阵、对照和字段说明；超过三层的嵌套列表改为分节。

## 6. 版本与跨仓库约定

- 本体版本以 `ddm/version.py` 为准；插件版本以各插件 `plugin.json` 为准；网站下载数据以 `docs/data/*.json` 为准。
- 文档中出现的版本必须能指回上述来源之一；不凭印象写“最新版”。
- 本体的公开插件接口在 [插件接口](../plugins.md) 中说明；新增能力要写“旧宿主是否可用”和最低版本。
- 插件 README 要写最低本体版本、依赖的其他插件、安装与更新方式；发布说明要与 GitHub Release 正文一致。
- 网站只展示已发布资产：下载地址来自 GitHub Releases，SHA-256 来自公开附件；本机重新打包的哈希不能替代。
- 跨仓库改动在三个仓库的 PR/提交中互相引用（链接到另一仓库的 PR 或提交），避免只在一侧留下结论。

## 7. 生命周期与归档

| 状态 | 进入条件 | 后续动作 |
| --- | --- | --- |
| 草案 | 方案仍在讨论 | 标明未定项；不合入发布说明 |
| 维护中 | 随功能持续更新 | 改动代码时同步更新，纳入文档检查 |
| 稳定 | 接口或流程已固定 | 修改需评审；保留兼容说明 |
| 冻结 | 不再主动更新，仍需可查 | 顶部说明冻结原因与替代文档 |
| 历史 | 已被新版本或新方案取代 | 移入 `docs/archive/` 或保留原路径并标注 |

归档只改变“是否代表当前行为”，不删除历史。发布说明发布后保持原文；补充说明追加在新的记录中，
不改写旧结论。清理文档前先检索引用、确认构建与检查不依赖该路径，再单独提交。

## 8. 索引与新增文档流程

`docs/README.md` 是每个仓库的唯一文档入口；子目录有 `README.md` 时，子目录文档由该索引收口。
新增或移动文档时按顺序完成：

1. 判断类型与归属目录，套用第 3 节的元信息；
2. 在 `docs/README.md` 或所属子目录索引中登记，写一句用途而不是只放标题；
3. 同步更新被影响的交叉链接和 `docs/repository-map.md`（本体）；
4. 运行本仓库的文档检查；
5. 与代码改动同一个提交，或单独一个 `docs:` 提交，说明验证范围。

检查发现“文档未被索引引用”“链接失效”“元信息缺失”时，修索引或修文档，不删除检查规则绕过。

## 9. 自动化校验

| 仓库 | 命令 | 覆盖 |
| --- | --- | --- |
| 本体 | `python dev/selfcheck_documents.py` | 元信息、索引可达、相对链接与锚点、本机路径、发布索引完整性 |
| 本体 | `python dev/run_checks.py --suite repository` | 上述检查加仓库规范、README、文件清单 |
| 插件 | `python tests/check_contributing.py` | 贡献流程、发布索引、增量记录、链接与文档入口 |
| 网站 | `npm test` | 站点内容、发布同步、开发文档入口与链接 |

检查只验证结构与链接，不判断技术结论是否正确；技术结论仍由对应专项和人工验收负责。

## 10. 模板

长期文档骨架：

```markdown
# 标题

> 类型：指南 ｜ 状态：维护中 ｜ 适用版本：0.7.x ｜ 更新：2026-11-14 ｜ 读者：贡献者

## 适用范围

## 操作步骤 / 设计说明

## 验证与未覆盖范围

## 相关文档
```

插件文档集：

| 文件 | 何时必须有 | 内容 |
| --- | --- | --- |
| `plugins/<ID>/README.md` | 始终 | 功能、最低本体版本、依赖、安装更新、已知限制 |
| `plugins/<ID>/DESIGN.md` | 有独立界面或后台流程 | 状态归属、线程/进程、失败与恢复 |
| `plugins/<ID>/FEATURES.md` | 功能多于一项 | 功能清单与验收口径 |
| `plugins/<ID>/ACCEPTANCE.md` | 涉及真实直播、录制或账号 | 人工验收步骤、预期结果、未覆盖范围 |
| `docs/changes/<ID>.md` | 始终 | 待发布条目、验收证据、提交/PR、发布注意 |

发布说明骨架：

```markdown
# <名称> v<版本> 更新说明

- 适用本体：<最低版本>（插件说明使用）
- 源码：<commit SHA>
- 验证：<命令与结果>
- 未覆盖：<真实直播/高 DPI/音频听感等>

## 变更

## 兼容与升级

## 已知限制
```

## 11. 例外与迁移

- 本规范生效前的文档保留原路径与原名；新增检查只要求长期维护文档补元信息，不要求历史记录改写。
- `docs/NOTICE.md`、各仓库 `NOTICE.md`、`LICENSE` 按法务原文保留，不受排版和元信息约束。
- 插件 `docs/releases/` 与 `sources.json` 是哈希固定的发布存档，只追加、不改写。
- 网站 `docs/` 是构建后的公开内容，开发文档放在仓库根目录 `development/`，不混入站点页面。
- 后续若迁移目录，先保留旧路径的薄索引或一次性提交全部链接更新，并在提交说明中列出验证命令。
