## 架构观察

对方使用 C#、.NET 8 和 WPF。Core 保存房间、布局、播放接口及调度规则；Infrastructure 实现平台协议、FFmpeg、音频和缓存；App 提供 WPF 控件及 ViewModel。Core 的程序集引用不包含 WPF、FFmpeg 或 NAudio，业务规则与具体实现的依赖边界较明确；主窗口及主 ViewModel 仍承担较多职责，不能仅凭分层认定所有部分都已解耦。

视频由 FFmpeg 解码，经 D3D11 视频处理和共享纹理，通过 D3D9Ex/WPF `D3DImage` 桥接到普通 `Image` 控件。`SharedVideoRenderer`、`SharedD3DImageSource` 和 `VideoSurfaceView.OnRendering` 的实际调用支持这一观察。硬件帧有视频处理操作，不能概括为绝对零拷贝。Windows App SDK 文件用于系统通知等能力，不能据此将主界面认定为 WinUI 3。

我们使用 Python/Qt，播放主要交给 [libmpv 包装层](../../ddm/player.py)，输出至 [原生视频窗口](../../ddm/video_surface.py)，再协调 Qt 界面、共享 Quick 弹幕和其他浮层。对方更便于把视频参与统一视觉合成；我们更多复用成熟播放器的解码、时钟和音频能力。两者的实现及维护成本不同，不需要因此更换开发语言。

## 值得学习的设计

| 方向 | 已观察到的做法 | 对我们的意义与代价 | 后续验证条件 |
| --- | --- | --- | --- |
| 请求调度 | `RemoteRequestGate/Queue/SingleFlight` 管理优先级、并发、排队过期、同资源合并、冷却和验证状态；启动路径构造门控 | 研究前台操作优先、后台错峰及重复请求合并；保留现有业务和插件的取消、凭据及重试边界 | 先采集具体慢操作，核对请求数量、等待时间和取消后旧结果；不能将不同账号/参数的请求误合并 |
| 全墙弹幕负载 | 共享帧调度；`DanmakuMonitorCoordinator` 将渲染指标交给全局背压控制，消息进入显示前经过准入并考虑优先房间 | 我们已有缓存、后台栅格化、共享 Quick 及单格数量限制；可研究全墙预算。减少准入会牺牲部分弹幕显示 | 多路高弹幕真实采集；同时检查帧耗时、消息显示量及重点房间，不能仅以消息更少证明渲染更快 |
| 布局过渡 | `BeginViewportResizePreview` 使用缩放/位移变换，结束预览后完成实际排列 | 研究减少过渡期间实际重排的次数；仍需处理最终布局、输入坐标与浮层一致性 | 先检查我们现有侧栏和缩放策略，避免重复实现；检查快速反向、连续拖动、高 DPI 和最后一帧对齐 |
| 全屏状态与恢复 | `WindowPresentationCoordinator` 区分全屏模式并保存恢复信息；静音后台房间可延后节流 | 学习显式状态、恢复快照和可取消后台任务；不直接替换已经验收的独立 Tile 呈现 | 进出及快速反向切换，检查隐藏格子、声音、弹幕归属与后台恢复；节流不能引入额外黑屏或错误画质 |
| 回溯数据复用 | 在现有播放压缩包上分出缓存；内存分段、租约、逐房间/全局配额和临时媒体额度 | 我们播放与 FFmpeg 录制/缓存读取分离，可研究复用输入；纯内存可能增加16路内存压力，不能直接替换长录制 | 先量化额外拉流、写盘和缓存占用；再测断流、换房、关键帧、音画同步、淘汰与导出期间的资源保留 |
| 回溯操作 | 时间范围选择、有声预览、GIF/MP4 导出及直接封装适用性判断 | 可先改善现有回放交互，再决定是否改后端；预览声音要能恢复用户的原选择 | 范围边界、预览退出、切房与导出；快速导出必须验证媒体条件，不承诺所有格式均可直封装 |
| 视频统一合成 | 视频成为普通 WPF 图像元素，与界面共同参与变换及叠放 | 是长期研究方向，可能减少原生窗口与浮层协调；也增加图形互操作、驱动和资源生命周期工作 | 独立验证 Qt 与候选视频纹理接口的兼容；检查多路硬解、帧延迟、GPU占用、跨屏、高 DPI、截图与退出，不直接重写播放器 |
| 音频交接 | 预备/提交/取消及连续性协调；响度校准与软限幅 | 我们已有音量均衡和声道路由，可学习异步交接与用户意图保存，不能把已有能力当成缺项 | 切换声音、换流、设备失效、取消/覆盖操作及预览后的恢复；实际听感与时间采集分别记录 |

## 平台适配与抖音的专项观察

B站已有账号、关注、画质和弹幕收发的较深入覆盖；虎牙和抖音有专门的取流及实时消息实现；Twitch/YouTube 取流依赖 yt-dlp，并分别有匿名 IRC 聊天和直播聊天接口接收。具体房间成功率、受限内容和长时间稳定性尚未实测，不据类名数量排名。

抖音部分值得学习的是职责拆分及验证结果回流：

1. `DouyinStreamResolver` 分开房间状态检查与页面取流；页面解析区分正常数据、安全验证和不支持的结构，区分页面编号与真实房间编号，整理 FLV/HLS 及画质候选。
2. 启动接入 `DouyinRealtimeDanmakuSource`。其构造路径是页面上下文、本地 C# WebSocket 签名、握手、候选服务器、连接管理、压缩/二进制解包、按消息 ID 去重，最终转换为公共弹幕消息。
3. `DouyinAudienceSource` 单独采集人数并管理轮询；需要验证时等待状态解除。普通视频播放进入公共 FFmpeg 播放链路。
4. 独立 WebView2 验证窗口让用户操作官方页面；完成后通过 Cookie 桥同步到普通网络请求使用的容器，保存加密副本，通知业务重试。通过安全验证不等于实现账号中心或互动发送。
5. 安装包保留旧轮询和其他连接构造类型，不证明这些都是当前启用路径，也不证明实时失败会自动降级。

**本样本没有确认抖音用户弹幕发送实现。** 已检查输入框可用性及 `SendChatTextAsync`，发送入口接入斗鱼和B站；抖音的 `SendAsync` 用于心跳及 ACK。WebSocket 接收握手签名不能当作发送接口方案。此结论只限本样本，不外推后续版本或官方网页自身的能力。

## 后续顺序与停止位置

1. 优先候选：针对已有真实证据的请求调度、取消语义及弹幕负载问题，做必要的小范围改进。
2. 功能候选：回放范围选择/预览；热度与活动关联房间等交互。先明确实际使用需求，不默认加入开发计划。
3. 长期研究：播放数据复用、统一纹理合成。先做隔离原型及相同条件对照，再决定是否迁移；成熟 libmpv 后端继续保留。

任何性能比较都需固定直播源、画质、实际帧率、解码、弹幕量及网络条件；后台降画质、减少弹幕或抑制解码须单独记录。真实启动、连续收展/全屏和长时间内存趋势不能由模拟功能测试替代。
