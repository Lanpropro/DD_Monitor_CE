# 久用卡顿与侧栏余顿：真实复现采集

BUG-070 仍待定位。本入口只记录证据，不修改播放、解码、缓存或节流策略；自动化测试验证采集器功能，不能代表真实卡顿原因或性能改善。

## 启动与复现

1. 在方便验收时自行退出原实例（如正在录制，先正常停止）。在仓库根目录终端运行 `run.cmd --diagnose-responsiveness`。正常双击 `run.cmd` 不开启本专项。
2. 启动后先正常使用约一分钟，记录启动时刻、布局、画面数量和侧栏数量。保持平时的直播、插件和使用方式；不要为了测试反复换账号。
3. 在刚启动与出现余顿时，各做同样的操作：收起/展开侧栏、切换卡片/列表、切换原有布局、悬停预览。每次记录本地时间（精确到秒）、具体操作，以及是界面迟缓、视频缓冲还是两者同时发生。久用问题保持到实际复现，不用固定短时间未卡顿推断已经解决。
4. 复现后继续约 15 秒，再正常退出。保留数据目录 `logs/responsiveness.jsonl` 和轮转文件 `.1`、`.2`，以及同一时段的应用日志。默认便携数据目录通常为仓库根目录；使用自定义数据目录时以实际数据目录为准。
5. 恢复普通运行只需正常启动 `run.cmd`。不必删除配置，也不需关闭长期监测开关。

## 记录内容与定位方法

- `start` / `stop`：会话编号、时间、相对运行时长。采样发生在新启动的实例，不会附加或重启已有实例。
- `sample`：每 10 秒记录累计进程 CPU 秒、工作集/私有内存、句柄数、Python 线程数，以及布局、画面/播放器/侧栏项/弹幕连接/退役线程/快照线程数量。线程数不是系统线程总数，也不是泄漏结论。
- `slow-call`：超过 16 ms 的已选方法执行耗时。覆盖布局切换、弹幕订阅同步、直播状态回填、侧栏折叠/卡片模式/头像条/重排、画面墙排布、预览检查与停止。`sample.calls` 同时给出各函数调用次数、总耗时和最大耗时；嵌套调用的耗时不可简单相加。
- `ui-stall`：100 ms 的界面心跳间隔达到 250 ms 时，在后台每秒最多记录一次主线程栈和正在执行的已选方法。栈只记录文件、函数、行号；不采集局部变量、账号、Cookie、聊天内容或直播 URL。

先按用户记录的时刻找到对应会话，比较刚启动与复现时的 `sample`，再用 `slow-call` 和 `ui-stall` 对应到代码路径。短于阈值、原生/GPU 阻塞或没有 Python 栈进展的问题可能仍需进一步专项采集；没有记录不能证明没有卡顿。原有 4 秒看门狗继续工作。

采样会增加少量定时器、线程和记录开销；这不是无扰动基准测试。单个文件约 5 MiB，最多保留两个备份，长时间运行可能覆盖早期记录，故刚启动基线可先另存。记录在本机，不自动上传。收到真实复现证据后才决定针对性修复与对照验收。
