# BiliBili ShadowReplay 录制与切片设计参考

记录日期：2026-11-04。状态：首轮源码研究完成，候选功能尚未实施。

研究目标是改善 DD监控室CE 从录制、回看、定位精彩片段到导出的流程。最值得借鉴的是独立的录播档案、可持续增长的回看时间轴、选区与标记、素材保存及后台任务，而不是立即把画面墙扩展为完整视频编辑器。

## 工作流与数据模型

对方将用户操作拆为：直播间 → 录播 → 素材 → 切片工程 → 导出或投稿。

| 对象 | 含义 | 对我们的参考 |
| --- | --- | --- |
| 直播间 | 值守的房间与启用状态，录制不依赖预览窗口持续打开 | 将录制任务与当前观看格子、临时窗口分开建模 |
| 录播 | 每次录制留下可查询的档案，有来源、时间、时长、大小及分段关联 | 用户按房间/日期找内容，不必先找文件夹 |
| 素材 | 从一个或多个选区生成的文件，保存来源范围与对应弹幕等旁路数据 | 录播缓存清理后，已保存的内容仍可继续处理 |
| 切片工程 | 引用素材的时间轴，保存裁剪、顺序、字幕、叠加和音频设置 | 把可反复编辑的工程与最终视频文件分开 |
| 后台任务/投稿 | 排队的处理工作、进度、取消和结果；投稿另有草稿与发布状态 | 操作窗口关闭不应丢失任务入口；导出与上传分别反馈 |

关键实现：[录播数据库](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/src/database/record.rs)、[素材数据库](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/src/database/video.rs)、[工程数据库](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/src/database/project.rs)。

## 录制与回看链路

当前前端是 Svelte 5/TypeScript，桌面宿主为 Tauri 2，Rust 后端负责媒体任务、SQLite 和服务接口。架构说明中仍有 Svelte 3、FFmpeg sidecar 等旧描述，不能直接套到当前源码。

- FLV 录制调用原生 `ffmpeg_utils::record_to_hls`，产出本地分段及 `playlist.m3u8`，周期更新时长/大小；结束时发布尾段并关闭播放列表。
- HLS 录制维护已下载分段、序号和本地播放列表，也处理 fMP4 初始化段、码流元数据及下载重试等情况。
- 活动录播的本地列表使用 EVENT，结束转为 VOD；这保留已录内容供回看，不把原直播源的滑动窗口误当完整存档。
- `handle_hls_request` 从缓存目录提供播放列表和分段，支持范围请求；前端播放器通过这一层读取已经录下来的内容。因此回看可以复用录制缓存，但分段可用时机和播放器缓存仍会增加延迟，不能直接等同于低延迟多路观看。
- 录制管理器与数据库持有任务/档案；素材生成可在外挂模式保存选区内弹幕，并映射为相对素材的时间，使素材不再依赖原录播弹幕文件。

源码：[FLV录制](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/crates/recorder/src/core/flv_recorder.rs)、[HLS录制](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/crates/recorder/src/core/hls_recorder.rs)、[列表语义](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/crates/recorder/src/core/playlist.rs)、[录制协调与本地服务](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/src/recorder_manager.rs)。

## UI 中最值得借鉴的部分

| 设计 | 当前源码可见的行为 | 价值与适用边界 |
| --- | --- | --- |
| 录播档案 | 按直播间筛选、排序、分页；列表/日历视图；显示日期、时长、大小与操作，支持批量选择 | 优先解决“录完之后去哪里找”；首版可先做列表，日历不是必要前提 |
| 回看工作区 | 视频与底部时间轴为主，右侧检查器切换选区、弹幕、标记及素材；有返回直播位置入口 | 将“看画面”和“处理时间范围”放在同一上下文，不把所有工具挤入观看底栏 |
| 多选区 | 拖动起止点、滚轮缩放、快捷键、启用/停用选区、起止时间与总时长 | 用户先粗选、多次核对，再决定分别保存或合并；快捷键应有可见按钮及输入焦点隔离 |
| 标记 | 按当前播放位置添加标记，列表与时间轴关联，保存备注和时间 | 可先用低成本标记保留“刚才那里”，随后回看补齐选区 |
| 弹幕热度与关键词 | 直方图和滑动窗口统计弹幕密度，阈值筛选核心区间，向两侧扩展并合并相邻推荐；可按关键词过滤 | 减少拖动整场录播找内容的时间；这是热度启发式，不是已经理解视频内容，刷屏或突发事件可能误导 |
| 生成确认 | 列出激活选区、每段和总时长；可分别/合并、填写备注、选择弹幕和编码、同时新建工程 | 确认“保存什么”和“怎样保存”，高级参数在提交阶段再出现；我们应保留更简短的快速保存入口 |
| 编辑器分区 | 左侧素材/音频/文字/贴纸，中间预览，下方时间轴，右侧字幕或选中项属性，顶部保存状态/撤销/任务/导出 | 工具随任务和选择变化，减少模式混乱；完整多轨界面对普通看直播用户过重，应独立进入 |
| 可恢复编辑 | 自动保存具有 pending/saving/error 状态及重试；编辑按操作提交撤销步骤，拖动中的状态不当成完成编辑保存 | 让用户知道编辑是否保存，撤销一次对应一次操作；选区/标记当前用本地存储，不能宣称都跨设备同步 |
| 公共任务中心 | 启动后立即显示任务，再与后端快照/进度合并；窗口内有统一入口和取消状态 | 不让“点了没反应”“窗口关了找不到任务”成为常态；不据此认定重启后能恢复未完成原生任务 |

源码：[回看工作区和热度推荐](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src/AppLive.svelte)、[时间轴](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src/lib/components/ArchiveTimeline.svelte)、[检查器](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src/lib/components/ArchiveInspector.svelte)、[生成确认](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src/lib/components/ArchiveClipButton.svelte)、[编辑器](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src/lib/components/project/ProjectEditor.svelte)。

## 后台任务和导出语义

`TaskManager` 使用优先队列、并发上限和取消状态，默认配置为一次1项、排队最多20项；这只是默认配置，不将所有后台工作都概括为同一队列。界面通过共享任务状态和进度订阅更新，窗口关闭与显式取消不是同一件事。

媒体执行层把完成进度留到封装收尾、输出发布后；临时文件有生命周期清理。值得学习的是结果可用时再宣布完成，而不是到达末帧就先显示100%。实际取消及崩溃恢复仍需运行测试，不能由代码结构保证。

工程通过时间轴引用素材入出点；字幕和叠加元素锚定片段，调整顺序时跟随，裁掉的字幕可暂时隐藏。自动保存会串行处理请求，并与后端变更合并。预览使用独立的音频主时钟与双视频切换等策略；适合编辑器，不直接用于替换我们的全部直播播放器。

当前普通生成界面传入显式编码参数，走重编码；未传参数的兼容接口仍有流复制分支。部分架构文档中“默认每选区直接复制”“简单工程直接复制原素材”的说明已经过时，不作为当前界面行为依据。起点、关键帧与实际素材覆盖区间要分别表达，不能承诺任意时刻的无损逐帧快切。

源码：[任务调度](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/src/task/mod.rs)、[前端任务状态](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src/lib/stores/tasks.ts)、[媒体进度与清理](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/src/ffmpeg/runner.rs)、[转码与复制分支](https://github.com/Xinrea/bili-shadowreplay/blob/e340951fa500d3977f5b9981329a1939650da82f/src-tauri/src/ffmpeg/clip.rs)。

## 与我们当前功能的差距及研究顺序

我们已有 [录制/回放会话与导出](../../ddm/recording.py)、[录制和缓存策略](../../ddm/capture_control.py) 及 [设置界面](../../ddm/dialogs.py)，保留最近数分钟、完整录制、原始流直存和重编码都已经存在。当前较明显的差距是录制之后的查询、预览、选区及任务反馈，没有必要先重写录制后端才开始改善。

建议的最小流程为：画面墙中的录制/快速保存 → 录播与回放列表 → 独立回看窗口 → 标记和时间选区 → 后台导出 → 打开成品位置。观看主界面继续承担观看任务。

| 阶段 | 候选范围 | 必须先确认的条件 |
| --- | --- | --- |
| 一 | 录播档案、快速保存入口、独立回看、起止选区、导出任务与取消/错误反馈 | 现有录制文件、缓存淘汰与未封口分段能否提供可靠可读范围；后台任务与录制生命周期分离 |
| 二 | 录制时打点、多选区、弹幕热度/关键词定位、素材备注及搜索 | 视频PTS、录制时间与弹幕时间如何对应；断流/重连、前一关键帧和缺失分段如何显示；已保存片段不被缓存清理误删 |
| 三 | 素材库、简单拼接、字幕、封面与更深入的剪辑能力 | 先明确用户真实需求及资源预算，再决定引入工程模型；完整多轨、AI及自动投稿不是首版必需项 |

不建议直接照搬统一缩放、默认重编码或后台录制所有关注房间。我们的多路观看场景需要保留原始流直存和快速导出，分别告知用户“快速保存”与“精确剪辑”的画质、边界和耗时差异；观看与录制各自拉流的问题也应单独测量，再研究缓存复用及由此增加的延迟。

后续若实施，在根 `run.cmd` 从真实录制验证：边录边回看、选择仍在增长的尾部、停止/换房/断流、缓存淘汰时导出、取消时不损伤旧成品、窗口关闭后找到任务、声音与弹幕时间对齐及高DPI操作。功能模拟和源码阅读都不替代这些验收。

本轮只保存研究结论，不启动账号登录、真实上传或软件功能改造。


## 后续实施决定：沿用本地 HLS 归档（2026-11-04）

用户要求直接参考本项目的大体思路，并以原仓库/原PR和验收记录跟踪连续改动，不逐次递增版本号。本轮在插件PR43与宿主PR161沿用“录播归档→活动EVENT→结束VOD→回看/选区→任务导出”链路，替代先前EDL增长适配；没有复制参考仓库的具体代码或引入其Rust/Tauri栈。

实际适配由现有FFmpeg进程写HLS，普通编码为TS、AV1为带初始化段的fMP4；原本体格子按钮、目录、编码、画质锁定及退出管理保留。Windows播放器通过软件内部127.0.0.1读取层访问已录分段，支持范围请求并避免持有清单阻止更新。快速保存与快照携带初始化段信息和分段租约，切片导出冻结可读VOD输入；原EDL录播保持可读，不自动迁移或删除。

本地测试及原生屏幕外出图验证归档语义、增长/定位、选区、跨轮转快速保存和收尾，不作为第三方项目或真实直播性能验收。后台自动值守所有房间、多轨工程、热度分析及投稿不在本轮范围内。
