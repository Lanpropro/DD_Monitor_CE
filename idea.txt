1. 发送弹幕
--------------------------------------------------------------------

想法
    在软件里直接往直播间发弹幕（弹幕面板底部加一条输入框）。

为什么走插件
    各家平台的发送方式差别太大（签名、票据、风控规则各不相同），
    塞进本体等于给每个平台都在核心里开一个分支。本体只该提供
    「调用谁去发」，不该知道怎么发。

现状
    ddm/plugins.py 定义了 DanmakuSender（available / send），本体负责在
    需要时调用它。plugins_user/danmaku_log/plugin.py 里已经有一份
    能跑的 B 站实现，走：

        POST https://api.live.bilibili.com/msg/send
        表单：roomid / msg / csrf / csrf_token / rnd / color / fontsize / mode / bubble

    参考：
      - https://github.com/SocialSisterYi/bilibili-API-collect/blob/master/docs/danmaku/action.md
      - https://www.cnblogs.com/addPath/p/15743000.html
    （另一条路是连上弹幕 WebSocket 后发 SendDanmakuMessage，见同一份 API 文档。）

卡在哪 —— 缺一个 bili_jct
    B 站发弹幕要 CSRF 票据 bili_jct，而当前登录流程**只存了 SESSDATA**：
      - ddm/login.py      扫码登录，读 cookie
      - ddm/web_login.py  内嵌浏览器登录，读 cookie
      - ddm/app.py        把 sessdata 存进配置、启动时 set_sessdata()
    所以插件里的发送路径是「写好了但没法端到端验证」——没有 bili_jct，
    接口会返回 -101 / -403 之类。

    要做的事很小：登录时把 bili_jct（和 uid，DedeUserID）一起抓下来存进
    utils/config.json，再让 bili 暴露出去给插件用。几个登录入口本来就在读
    cookie，多拿两个键而已。

    验证方式：拿自己的号发一条到自己的直播间。注意这是高频风控动作，
    别写成循环测试。

还要做的
    - 面板底部输入框（本体的小改动），或者把输入框也做成插件往面板上加
    - 未登录 / 没有 bili_jct 时输入框要置灰，并说清缺什么
      （DanmakuSender.available() 已经返回原因，界面直接用）

2. 录像
--------------------------------------------------------------------

想法
    把某一路直播录到本地。

为什么走插件
    录制策略（时长切片、码率、存哪、什么时候自动开始）因人而异，
    而且它需要拉第二条流，属于「旁观者」不该占用本体播放器的资源。

现状 —— 接口已经铺好，只差一个插件
    本体每次取流成功都播报 stream.resolved，事件里带 StreamSource：

        source.url       可直接播放的 http 流地址
        source.headers   拉这个地址**必须**带的请求头
        source.channel   app / web / 插件平台的 kind
        source.room_id / uname / title / quality

    取流结果同时记在格子上（tile.stream_url / tile.stream_headers），
    插件也能直接取。

    请求头一定要用事件里给的那份，不要自己拼：B 站 app 通道的地址**不能带**
    Referer、web 通道**必须带**，弄反了 CDN 直接 403。

要做的
    - 一个 plugins_user/record/plugin.py：
        on_event 里收到 stream.resolved 就 subprocess 起 ffmpeg（-c copy）
        停止/切房间时收到 tile.stopped / room.offline 就收尾
        tile_actions 加「开始录制 / 停止录制」
    - 断流要考虑：本体重连会再播一次 stream.resolved，插件的录制要能续上
      或者切成新文件，别默默停掉

3. 接别的直播平台（抖音 / YouTube / Twitch）
--------------------------------------------------------------------

想法
    除了 B 站，也能挂别的站的直播间。

为什么走插件
    本体只需要「房间号 → 房间信息 + 一个 http 流地址」。把这两件事交出来，
    播放、布局、音量、弹幕面板全都不用改。反过来，把各站解析塞进本体，
    核心就会被一堆各站特有的签名/防盗链逻辑淹没。

现状
    ddm/plugins.py 定义了 Platform（matches / normalize / room_info /
    rooms_status / play_url），骨架在 plugins_user/_template_platform/plugin.py。
    房间号写成 <kind>:<房间号或链接>，例如 douyin:123456，用来和 B 站的
    纯数字房间号区分。同一个 kind 注册两次会直接报错，不静默覆盖。

要做的（每一站都是独立的一小块）
    - 解析：怎么从用户输入（链接/短链/房间号）拿到房间标识
    - 房间信息：标题、主播、封面、是否在播
    - 取流：拿到 http(s) 地址
        Twitch 有签名 token，地址要连着 token 一起算，且会过期
        YouTube 要解析 manifest，可能是 HLS 而不是 FLV
    注意 VLC 插件集**没有 TLS 插件**，地址尽量给 http；给不了就得先确认
    能加上 TLS 支持，否则这条路走不通。

    另外本体的弹幕面板目前只认 B 站的协议，别的站的弹幕接进来是另一件事
    （可以先用 Plugin.on_event 往外转发，不进面板）。

4. 顺手记两笔（小、但不该忘）
--------------------------------------------------------------------

- selfcheck_offline_badges.py 目前是红的，而且不是这次改动弄红的：
  它断言「重新开播后 room["live"] 是 True」，但自检不联网、取流必然失败，
  失败会触发 _offline_tile() 把 live 置回 False。要修得先定：
  取流失败的格子到底算不算「在播」——这是产品判断，不是 bug 修复。

- 声道（只播左/只播右）在真实回放里还没确认生效。已经排除的：
  :stereo-mode 作为 media 选项、--audio-filter=remap 的 aout-remap-* 写法，
  用 WASAPI 环回录音量过，左右声道内容都没变。还没试的：remap 在实例级用
  remap-channel-* 真名再试一次；或者进程内 audio_set_callbacks 改采样
  （回调确实会触发、缓冲区确实能改，只差把采样格式对齐）。



自定义布局

单格独立录制（方案已确认，暂不实现）
- 每个播放格拥有独立录制按钮和录制状态；互不影响。
- 使用 FFmpeg 子进程直接录制当前直播流，优先 `-c copy`，默认保存 MKV，停止后可选无损封装为 MP4。
- 一次录制会话绑定主播而不是格子：交换画面时，录制标记和任务跟随主播，避免同一文件混入两位主播。
- 断流重连后写入新分段（例如 `_02`），不把断流前后强行拼接。
- 文件名包含主播名、房间号、开始时间；设置中提供保存目录和磁盘空间下限。
- 软件重启后不自动继续录制，只保留上次保存目录。
