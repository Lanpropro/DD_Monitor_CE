## 1. 先量内容边界，不要凭截图框猜

用户画的框只是**位置示意**，不是「窗口必须这么大」。真实尺寸只能从像素量出来。

抽 3 帧（时长的 20% / 50% / 80% 处）取并集：

```powershell
ffmpeg -ss <t> -i X.mp4 -frames:v 1 out.png
```

```python
im = cv2.imread(p, cv2.IMREAD_GRAYSCALE)
nz = im > 14                                   # 非黑
cols = np.where(nz.sum(axis=0) > h * 0.02)[0]  # 该列有 2% 以上非黑
rows = np.where(nz.sum(axis=1) > w * 0.02)[0]
```

**实测（2026-09-22 那批 4K 录屏）**：

| 素材 | 内容边界 | 比例 |
| --- | --- | --- |
| 布局切换 / 9格 / 左声道 / 右声道 / 弹幕 | x 0–3270、y 0–1821 → **3271×1822** | 1.795 |
| 切换竖屏 **前 80%** | x 0–1362、y 0–2159 → **1362×2160** | **0.631** |
| 切换竖屏 后 20% | 3271×1822（横屏） | 1.795 |

⚠ **同一段素材里窗口形状可能变**（`切换竖屏.mp4` 前 80% 竖屏、后 20% 横屏），
所以要**分段量**，不能只抽一帧就下结论。

## 2. 裁切 + 缩放到工作尺寸

```powershell
ffmpeg -y -i X.mp4 -vf "crop=3271:1822:0:0,scale=1600:-2,fps=30" `
  -c:v libx264 -crf 23 -preset veryfast -an out.mp4
```

- `crop=w:h:x:y`
- 工作宽：横屏 **1600**、竖屏 **800**（够 01/02 放大到 2.2 倍还不糊）
- 4K/60fps → 窗口尺寸/30fps：**113MB → 2.2MB**，渲染快一个量级

## 3. 窗口比例必须跟素材走

- ❌ **不要硬套 16:9 / 9:16**。`切换竖屏.mp4` 的真实竖屏比例是 **0.631**，
  硬套 9:16 的结果就是「右边留一块黑边 + 左边正常内容被切掉」——
  用户 2026-09-22 指出的正是这个。
- composition 里的容器尺寸要按素材比例反算：
  宽 1382 → 高 `1382 / 1.795 = 770`；竖屏取 642×1017（642/1017 = 0.631）。

## 4. `object-fit: cover` 的中央裁切陷阱

cover 默认按**中央**裁。素材内容不在正中时就会取到黑：

- `切换竖屏.mp4` 的内容只在源画面**左侧 1/3**（bright cols 0.7%–34.9%），
  cover 取中央 9:16 → **整块全黑**。
- 裁到内容边界之后这个问题自然消失；如果暂时不能预裁，用 `object-position`
  对准内容中心（当时用 `18% center` 临时救过场）。

## 6. composition 侧的坑（全部实测踩过）

1. **不要补间容器的 `width`/`height`** —— 只要容器在变形，里面 `<video>` 的帧就整个丢失
   （竖屏窗口会全黑，`drawElement` 捕获到空帧）。需要「16:9 → 9:16 变形」就得改设计，
   或者预先把两段素材渲好。
2. **不要写 `will-change`** —— SCRIPT 第十节那条禁忌，视频层同样会被按布局尺寸裁掉。
3. **`<video>` 必须有 `data-start`**（否则 lint 报 `media_missing_data_start`）；
   而 `data-media-start` 让渲染器去 seek 时会遇到首帧没就绪 → **预裁成独立文件更稳**。
4. 预览/调试用 `tools/probe-variants.mjs`（走 CDP 直截）能区分「DOM 就黑」还是
   「只有渲染器黑」，这一步省了大量猜测。

## 7. 本次提取的音乐素材（2026-09-22）

来源：`Video_reference/【合集】一口气看完17个Microsoft微软官方广告.2022年-Microsoft_-_Loop.550193601.mp4`
（1920×1080 / 25fps / **60.0s**，含 AAC 立体声）。

- 提取到 `assets/bgm/ms-loop.wav`（48kHz 立体声，60.09s）
- RMS 结构：**35–58s 是最连贯、最响的一段**（≈23s）；
  10.5–12s / 24–27s / 32–36s 有段落间隔（合集拼接留下的断口）；58s 后渐弱收尾
- **节拍网格（用 onset 峰值定位，2026-09-22）**：拍点中位间隔 **0.1905s**
  （≈157.5 BPM 的八分音符；实测中位 0.192s）。第一个峰在 0.16s，之后按 0.1905s 递增，
  所以**网格点 = 0.1905 × n**，与实测峰值的偏差 < 0.02s。
  自相关那条路给出的 240 / 163 BPM 都不可靠（曲子是十几个广告配乐拼的，不是单一稳定节拍），
  **对齐动效一律以 onset 网格为准**。
- **01 的对齐结果**：模块逐块拼入的 stagger 从 80ms 改成 **0.1905s**（每块正好落一拍）、
  起点 **5.334s**（= 0.1905 × 28）；推进放大 **6.858**（×36）、月光 **8.382**（×44）、
  文字与定格推进 **8.763**（×46）。相机曲线**没有动**（那是照参考片量的，不参与对齐）。
- 前 2.25s 是低音量前奏（-20 ~ -34 dB），**不需要静音**；0–0.5s 有一段广告开头音效
  （-19 dB），若嫌吵就把前 0.5s 静音。
